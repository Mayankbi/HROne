# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-75) | Returns `{"status": "ok"}` unconditionally without checking if MongoDB is alive. Specification requires returning 503 if MongoDB fails ping. | Kill or disconnect MongoDB; `/health` still returns 200 instead of 503. | Added `client.admin.command("ping")` inside a try-catch block, raising `HTTPException(503, "MongoDB ping failed")` on exception. |
| 2 | `compute_late_minutes` (lines 33-38) | Replaces punch-in date directly and checks `minutes > 10` on whole minutes. Also does not consider attendance date or overnight shifts (R1, R2). For 09:40:01, `(punch_in - start).total_seconds() / 60` truncated to int is 10, returning 0 instead of 10. | Punch-in at 09:40:01 gives `late_minutes = 0` (contract specifies 10). | Recomputed elapsed seconds: `diff_sec = (punch_in - shift_start).total_seconds()`. If `diff_sec > 600`, return `int(diff_sec // 60)` from shift start. |
| 3 | `compute_work_hours` (lines 40-42) | Uses Python's built-in `round()`, which performs banker's rounding (round half to even). Rule R4 strictly mandates half-up rounding. | Work duration of 9.125 hours rounds to 9.12 instead of 9.13. | Replaced with `Decimal.quantize(..., rounding=ROUND_HALF_UP)`. |
| 4 | `compute_overtime` (lines 44-48) | Uses naive datetime parsing (`datetime.fromisoformat(date_str)`), ignores the 30-minute threshold rule (R3), and fails for overnight shifts where shift end is the next calendar day. | Punch-out 25 minutes after shift end yielded 25 minutes overtime instead of 0. Overnight shifts gave negative durations. | Added check that overtime is only counted if diff >= 1800s (30 min); advanced shift_end by 1 day if `shift_end <= shift_start`. |
| 5 | `create_employee` (lines 78-85) | Employs check-then-insert (`find_one` then `insert_one`) rather than relying on a unique database index. Concurrent creates cause race condition. Also allows `shift_start == shift_end` (violating contract), and stores naive datetime. | Concurrent duplicate `POST /employees` creates duplicates or raises unhandled 500. `shift_start == shift_end` returns 201 instead of 422. | Added unique index `emp_code` on startup; caught `DuplicateKeyError` and returned 409; validated `shift_start != shift_end` with 422; converted `created_at` to UTC datetime and epoch ms. |
| 6 | `list_employees` (lines 89-97) | Pagination formula used `skip = page * page_size`, which skips page 1 completely (starting at page 2). Also counted all documents in collection rather than filtered query count `q`. | Requesting `page=1` returned items starting from index 20 instead of 0; `total` did not respect `department` filter. | Fixed skip to `(page - 1) * page_size` and changed count to `db.employees.count_documents(q)`. |
| 7 | `punch_in` (lines 100-121) | Race condition with check-then-insert `find_one` then `insert_one`. If employee is unknown, raises `KeyError` -> 500 instead of 404. Also generated internal `"id"` from `_id` violating contract (`_id` must not appear). | Concurrent punch-ins both return 201; punch-in for nonexistent employee returns 500 instead of 404. Response includes prohibited `id` field. | Verified employee existence (404); relied on unique compound index `(emp_code, date)` to catch duplicate punch-ins atomically (409); removed `id` field; formatted epoch ms and dates per schema. |
| 8 | `punch_in` date calculation (lines 102-103) | Extracted date using server local timezone `ts.date().isoformat()` instead of IST calendar date (R1), and completely ignored overnight shifts where punch-in before `shift_end` belongs to previous day. | Night shift worker punching in at 05:30 IST got today's date instead of previous day's shift date. | Implemented `determine_attendance_date` with IST conversion and overnight previous-day rule per R1. |
| 9 | `list_attendance` (lines 124-150) | Loaded all matching documents into Python memory with `list(db.attendance_logs.find(q))` and sorted in Python. This will crash or crawl at 100,000 documents. | Memory spike and latency timeout when listing attendance over large datasets. | Performed `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` directly in MongoDB using indexes. |
| 10 | `list_attendance` validation & fields (lines 126-150) | Did not validate `date_from > date_to` (must return 422). Returned string `"id"` from `_id`. Did not format nested dates in history to epoch ms. | Passing `date_from=2026-07-10&date_to=2026-07-01` returned empty 200 instead of 422; returned internal `id` field. | Added validation `if date_from > date_to: raise 422`; stripped internal `_id` and formatted response according to `AttendanceRecord` schema. |
| 11 | Epoch Milliseconds boundary handling (global) | Accepted arbitrary timestamp values or converted using naive `datetime.fromtimestamp(punched_at / 1000)`. Did not enforce minimum milliseconds (`>= 100000000000`) or whole-second truncation (R1). | Passing seconds-looking integers (e.g. `1783312500`) was accepted or caused year 1970 date distortions. Millisecond fractions produced floating-point inaccuracies. | Validated `EpochMillis` schema bounds (`100000000000` to `4102444800000`) with 422; truncated to whole seconds (`ms // 1000`) before calculations per R1. |

Also note anything you looked at and decided was **not** a defect, and why:
- `db = client[os.getenv("MONGO_DB", "attendance_db")]`: Reading environment variables at module top-level with fallbacks and `.env` loading is standard in FastAPI starter applications; we kept this while ensuring real environment variables override defaults.
- IST timezone definition `timezone(timedelta(hours=5, minutes=30))`: The standard library timezone representation is lightweight, correct, and avoids external pytz dependencies.
